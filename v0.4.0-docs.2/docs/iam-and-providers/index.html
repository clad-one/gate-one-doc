IAM, IdPs and provider types

Who authorizes, who identifies, and which authProvider type Gate One uses.

IAM services cover authorization and configure the identity providers (IdPs) they trust.

Gate One sits between the user, an IAM/authorization source and an IdP. The schema’s authProvider.type is a provider type: it selects who Gate One asks to verify a request and obtain identity/authorization claims. It is not an IAM by itself.

auth.identity is where Gate One enforces route policy. An IdP that also carries roles, scopes and claims is acting as the IAM for that deployment; Gate One still does not store users or assign rights.

The three roles

RoleQuestion it answersExamples
IAM / authorizationWhat is this account allowed to do? Which tenants, roles, audiences and token lifetimes apply?cladone-auth, Keycloak, Entra ID, Auth0, Okta
IdP / identificationWho is this human?Google, Microsoft, Keycloak as an upstream IdP, a corporate LDAP/SAML directory
Gate One / enforcementIs this request authenticated, and does it satisfy the route policy?authProvider, auth.identity, MCP scope checks

An IAM can also be an IdP: Keycloak, Entra ID and Auth0 all do both. Gate One connects to the IAM, and the IAM configures the IdPs it trusts.

Two valid shapes:

  1. With a separate IAM (recommended for several IdPs). The IAM owns the upstream IdP configuration (tenants[].upstreams), local policy, user grants and token issuance. Gate One points at the IAM with one oidc provider.
  2. Without a separate IAM. Gate One points directly at one OIDC provider that acts as both the IdP and the IAM/authorization server. It authenticates the user and emits the roles, scopes and claims Gate One enforces. This is simpler, but the provider must supply the claims your routes need.

In both shapes, Gate One enforces auth.identity per route; the IAM does not decide which application route a user may call. An IdP that only authenticates (for example a plain Google login) does not provide application roles; use an IAM/broker or another claim source if you need them.

http is accepted as a deprecated alias of http-bridge so existing configurations keep working. New configurations should use http-bridge.

oidc

Gate One is the OpenID Connect relying party: discovery, authorization code + PKCE, state/nonce, JWKS, signed session, RP-initiated and back-channel logout. It hosts the login surface on loginBaseUrl.

Use it for a direct OIDC IdP or for a cladone-auth tenant. This is the only provider type that combines a browser session with local revocation state (bbolt or Redis).

jwt

Gate One validates a bearer token against a JWKS. It never hosts a login page and never issues a token. Use it for APIs and MCP clients, not for a browser session.

http-bridge

Gate One delegates verification to an HTTP service that implements the Gate One HTTP bridge contract. The bridge is where non-OIDC technologies are adapted: SAML, LDAP, mTLS, API keys, a legacy session service, or auth-bridge in front of Keycloak.

Gate One only calls /auth, /auth/mcp and /health, and redirects the browser to the bridge’s login page. The bridge owns the protocol and, usually, the session cookie. See the HTTP bridge contract for endpoints, headers and status codes.

There is no grpc-bridge provider type today. The gRPC binding is planned for the broker-side identity adapters, not for authProvider. If it becomes useful, it will be a new type rather than a silent change to http-bridge.

dev

The embedded provider exists for onboarding and tests. It is loopback only, has real alice/bob accounts, and must not be exposed to a network.

Internal OAuth IAM: cladone-auth

cladone-auth is the optional internal OAuth/OIDC IAM. It is a small multi-tenant issuer with a broker-side user directory:

  • it federates external IdPs (Google, Microsoft, Keycloak, …) configured per tenant under tenants[].upstreams;
  • it applies local policy: tenant, roles, audiences, allowed domains, admin emails, claim mappings and user grants;
  • it stores one external identity link (issuer, subject) per federated user; it never recreates the IdP account;
  • local and federated users both carry roles/scopes/claims, managed by the admin CLI;
  • it emits its own Ed25519-signed ID/access/refresh tokens and publishes JWKS and discovery;
  • it publishes the revocation keyspace Gate One reads for a global logout.

It is deliberately lighter than Keycloak: one Go binary, one JSON file, Redis optional for multi-instance state, no realm/theme/admin console to operate. That makes it a good fit when you need several IdPs, normalized rights or local policy, but do not need a full IAM suite.

flowchart LR
  GO["Gate One<br/>authProvider + route policy"] -->|"authorize + token"| BROKER["cladone-auth<br/>tenant mycompany"]
  BROKER -->|"upstream login"| G["Google"]
  BROKER -->|"upstream login"| M["Microsoft"]
  BROKER -.->|"optional local password"| L["Local account<br/>PBKDF2"]
  BROKER -->|"roles, scopes, claims"| GO
  USERS["user directory<br/>local + federated grants"] --- BROKER
  MAPPINGS["claim mappings<br/>IdP claims -> roles/scopes/claims"] --- BROKER

The recommended path is external IdPs: there is no password store to protect and no password-hash cost at login. Local accounts (localAccounts) are optional for small deployments; they use PBKDF2 and add the operational burden of a credential store.

Claim mappings are evaluated on every federated login. Per-user grants are applied to both local and federated users, and changes take effect at the next login.
